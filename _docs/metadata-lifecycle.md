# Lookup, review and imported-field lifecycle (#19)

WatchNext offers manual entry, YouTube link lookup and explicitly third-party **Кинопоиск Unofficial** search on Add title. Manual entry remains independent. Lookup returns suggestions only: search candidates require explicit selection/detail lookup, and Apply proposal explicitly replaces details. Moods remain the user's choices. Missing type/runtime/episode numbering must be completed with the existing strict title validator. Genres unsupported by the existing comma-separated editor remain incomplete rather than silently becoming different genres.

An applied episodic proposal requires an explicit typical-duration checkbox, validated again on the server. Switching between full-item and episode meanings clears the old runtime/numbering inputs; changing type/runtime resets that confirmation. Equal seconds with a different meaning are a user correction, not provider-verified typical runtime.

## Server-owned review and save

`beginReview` / `selectReviewCandidate` in `lib/metadata/reviews.ts` validate actual group, selected profile, request origin and session before provider access, then recheck after asynchronous lookup. Credentials/configured providers remain behind `server-only` entries. Actions accept source/query or a bound search handle/candidate choice; never a form-supplied provider identity. Only normalized, safe projection fields enter a review.

Review handles are random 256-bit values. Only hashes are stored in `metadata_reviews`, bound to actual group/member and the current session credential hash. Candidate and detail snapshots expire after **10 minutes**, with at most 20 retained per session. Oldest snapshots can expire early when this bound is exceeded. Snapshot JSON contains the normalized original acquired values, safe provenance and original retrieval deadline, not raw API bodies/keys/headers. Expiry maintenance actually deletes expired snapshots; successful save consumes its snapshot atomically. Invalid, other-member/group/session, expired or replayed consumed handles cannot authorize a save. A stale original API deadline also blocks saving.

The client stages each proposal and guards responses with a generation counter. Changing query/source, cancelling, or starting a newer request invalidates earlier results. A late response never changes existing editable fields. Applying is explicit and warns which fields will be replaced; manually entered moods remain. Lookup failure preserves the current form and manual save stays available. An active applied review retains its origins when switching the lookup selector; it is not silently relabeled as manual data. Starting a fresh manual entry is an explicit clear-details action. Pending save disables form, replacement and reset controls.

`saveReview` validates completed fields and safe optional links, then calls the existing `saveTitle` provider branch with server-held identity. No second insert path exists. A pre-commit callback writes origins/deadlines and consumes the snapshot inside the same shared-save transaction. A provenance/storage failure rolls back title, moods/genres, contribution and review consumption together. Manual-match attachment confirmation, collisions, already-added attribution, archive restoration and preserved existing metadata/history use #13/#15 semantics. Existing-entry additions/attachments do not overwrite metadata or invent new acquired provenance.

Per-field ownership is recorded in `metadata_fields` for title, type, duration, genres, source/watch/cover links. Unchanged normalized prefill stays **provider** owned; actual canonical user corrections are **user** owned. Moods, numbering choices, notes, ratings and progress are independently authored. Merely reviewing or saving does not convert imported data to user authorship. The table stores origin, trusted retrieval/deadline and a cleared flag, **not an original-value copy**. After save the temporary review snapshot is gone. Edits change ownership only for genuinely changed fields; unchanged fields keep provider ownership/deadlines.

## Refresh and deletion

YouTube provider-owned fields expire at the trusted retrieval-plus-30-calendar-days deadline from #16/#17. [YouTube policy III.E](https://developers.google.com/youtube/terms/developer-policies), rechecked October 16, 2026, requires refreshing or deleting public non-authorized data within that period; it does not guarantee correctness until the deadline. No OAuth/private-owner data is requested.

`refreshTitleMetadata` guards actual group/profile/target/origin and refreshes the stored server-held identity through the configured adapter. Only accepted, **still-provider-owned** fields are replaced/renewed, inside one transaction. Concurrent explicit corrections win because ownership is re-read after the provider await. Missing/unverified fields are not granted a new deadline. Failed/unconfigured/offline/not-found refresh cannot renew old timestamps; at/after deadline acquired values are cleared. A storage collision/failure rolls refresh changes back. No automatic retry or quota evasion exists.

`expireMetadata` clears actual expired values: title/key, type, duration and links become NULL; acquired genre rows are deleted. IDs/provider identity, archive/contributions, numbering/history and all notes/ratings/progress remain. Provenance retains origin/deadline/cleared status for guarded refresh, without an original-value copy. User corrections/history/moods remain preserved. Delivered picker projections exclude unavailable/null runtime and require known positive full/typical duration and valid metadata.

Cleanup enables SQLite `secure_delete=ON`, so removed snapshot/metadata cell contents are overwritten in the active database rather than left as ordinary freed-page copies. A file-byte regression checks the synthetic title and derived key disappear. This is not a claim about OS backups, filesystem snapshots or a powered-off computer.

Nullable imported values render honest Metadata unavailable / Content type unavailable / Duration unavailable states. Active/archive/details/add-summary/edit/shared-save reads run maintenance before exposing data. Details provide refresh and authorized correction paths; archived entries retain restoration rules. Empty edit inputs are not substituted fake titles or zero runtime. Manual validation still requires real title/type/positive duration before save.

PM clarification [#19 comment](https://github.com/xiaodlb/watchnext/issues/19#issuecomment-6212866129) bounds recovery under D10: an authorized contributor may explicitly fill an expired NULL type using current revision and existing identity confirmation **only with unchanged compatible numbering/history structure**. Known non-null type changes and numbering changes with history stay blocked. Cancelling a confirmation writes nothing; stale revisions/wrong access still fail. No expired original type copy is retained to implement this recovery.

## Runtime and explicit maintenance

Shared connection startup/reuse and every metadata-bearing service read clear expiry before returning values. Each batch processes at most 250 fields; if more remain, a guarded read fails safely for retry instead of displaying uncleared data. Process-local unreferenced timers wake at the next known deadline, checking at least once per minute for new reviews/deadlines; each callback performs one bounded batch. They stop on connection close and do not keep CLI processes alive. Read-boundary checks remain authoritative if a timer is delayed or storage is busy.

Run **`pnpm metadata:maintain`** for explicit offline cleanup of the configured, already-initialized local database. It loads the same optional `.env.local`, accepts no path arguments, makes no provider request, checks the schema, and handles at most 100 batches per invocation; repeat if more remain. It prints counts or a generic recoverable error, never credentials/SQL/paths. Verification invokes the underlying script with a separately initialized temporary `WATCHNEXT_DATABASE_PATH`; normal user data is never a test fixture.

**When the app/computer is stopped, no JavaScript timer or external scheduler runs.** This project installs no external scheduler. Run maintenance before a deadline if keeping the local file while the app is stopped; otherwise the next startup/read clears expired values before any metadata is displayed or used. A restart after an offline gap does not renew provenance or pretend data stayed fresh. This is a local process/read enforcement mechanism, not a guarantee that a powered-off computer physically erases bytes on a wall-clock deadline.

## Delegated local academic Кинопоиск snapshot policy

Adopted under the October 15 autonomy directive quoted in [plan.md](plan.md), as explicitly bounded by the groomed #19 scope. This is a project storage policy, **not verified licensing, account entitlement or an official partnership**. The [Unofficial OpenAPI](https://kinopoiskapiunofficial.tech/documentation/api/openapi.json) still documents version 2.0.1, the service endpoints and header; its nullable `filmLength` does not establish units/episodic meaning. The [homepage](https://kinopoiskapiunofficial.tech/) and [rates](https://kinopoiskapiunofficial.tech/rates), rechecked October 16, exposed JavaScript-only shells in this check. No explicit text-snapshot persistence prohibition was established from the inspected material; that limited result is not proof of rights or permanent free access.

Configured lookup/review/save remains functional for **local academic text snapshots**. At the review integration boundary, `provider_policy_unverified` adapter output is labeled `academic_local_snapshot_30_days` with an app-chosen 30-day refresh-or-delete deadline. The per-field expiry/refresh machinery enforces that conservative project lifetime as well. This choice limits stale local retention while preserving the requested working provider flow; it does not claim the provider mandated exactly 30 days. External account/terms verification remains disclosed. Any explicit restriction encountered during actual authorized setup must be followed.

No provider covers/image binaries are imported/cached from this service, no streaming link or anime classification is inferred, and every movie/episode runtime remains a manual confirmation until units/meaning are verified. User-authored corrections/history persist independently. This narrow policy supersedes #16/#18's provisional blanket verify-before-persistence handoff for local academic **text** snapshots, while keeping all access/runtime/image-rights limitations truthful. The adapter itself still reports its unverified external policy; the server review/storage integration records the chosen project policy.

## Verification boundaries

All automated provider cases are synthetic/mocked, with injected adapters/transport and controlled clocks. No authenticated availability/quota/license claim follows from a passing test. Migration, handle authority, field origins, duplicate/restoration, rollback, deadline edges, failed/successful refresh and both-member history preservation have isolated fixtures. Browser verification uses an explicitly imported **test-only** outbound transport preload and temporary initialized database; production startup has no debug/provider-bypass route or hook. No real keys, normal user database, purchase, account registration, scraping, playback or image download is required.

The supported portable whole journey is `pnpm test:e2e` with the pinned development-only Playwright/Chromium setup in [testing guidelines](testing-guidelines.md). The older focused `node tests/fixtures/metadata-browser-check.mjs` accepts explicit installed `WATCHNEXT_BROWSER_MODULE` and `WATCHNEXT_BROWSER_EXECUTABLE` after a build; it covers review/save/reload/expiry/refresh and scans fixture credentials. Its optional local artifact retention is not the default/supported whole-suite workflow; never retain private links/tokens, and clean owned inspection artifacts. No browser automation library is a production app dependency.
