## Account registration, login and logout — issue #32

`/register` and `/login` are accessible forms; dynamic `/account` reads the actual separate account credential and displays its database username and current account memberships, or safely redirects to fixed `/login` when anonymous/expired/revoked/tampered. Storage failure returns a safe retry view. The landing clearly labels existing legacy group entry separately. No legacy member, history, invitation or membership is claimed by registering/logging in. Password recovery is described below.

Protected JSON `POST /api/account/register`, `/login` and `/logout` accept only the operation's username/password/confirmation fields (logout accepts `{}`). The method must be POST, Origin must exactly match validated `WATCHNEXT_APP_ORIGIN`, and cross-site Fetch Metadata is rejected. Host/forwarded headers grant no authority. Body reading is capped at 4096 bytes and ten seconds; unsupported content types/shapes/fields fail safely. Native forms explicitly use POST before hydration; JavaScript sends JSON without query secrets. There is no caller-controlled return target: only fixed `/account` or `/login` navigation is supported. Error responses contain actionable safe text, never input passwords, SQL, paths, raw exceptions or credentials. Sensitive API responses are `private, no-store`/`no-referrer`; account pages are dynamic and not cached publicly.

Username outer whitespace is trimmed, 3–32 ASCII letters/digits/underscore/dot/hyphen retained with display case; lowercase key uniqueness is enforced transactionally. Passwords contain 12–128 Unicode code points, with well-formed Unicode required; no trimming/normalization/composition rules, including exact spaces and combining characters. Confirmation must match exactly. Forms retain username on failure, clear password/confirmation after each request, disable duplicate pending submissions and focus announced feedback. Registration duplicates are actionable; valid-name unknown and wrong-password logins share `Username or password is incorrect.`

Native asynchronous `crypto.scrypt` uses version 1, N=131072/r=8/p=1/maxmem=268435456, random 16-byte salt and 64-byte key. Only that exact supported tuple and fixed lowercase hex hash/salt lengths are accepted from storage before work; malformed/unknown rows perform dummy work at the same real cost and fail safely. `timingSafeEqual` compares fixed 64-byte digests. This prevents the skipped-hash discrepancy, **not** a promise of identical whole-request timing or external security certification. Current primary references inspected October 18: [Node24 crypto](https://nodejs.org/docs/latest-v24.x/api/crypto.html), [OWASP scrypt storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [OWASP authentication/errors/throttling](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html). The project's explicit 12-character minimum remains its product rule.

One process-shared pool admits two active hashes and eight waiting jobs, with a 30-second queued timeout and safe busy/retry errors. Slots release on success/error/expiry; crypto defaults are never reduced for tests. Login admits five attempts per normalized username/15-minute fixed window, reserving before work to bound parallel submissions; success clears that key. Signup has five per normalized username plus thirty total attempts/15 minutes, including failed/duplicate admitted submissions. Expiring maps hold at most 2048 names; full maps reject additional names instead of evicting live throttles. No arbitrary forwarded IP is trusted. Limits are **process-local**, reset on process restart, and do not provide distributed abuse protection or persist account lockouts. Bounded queue errors consume the admitted attempt conservatively.

Registration's account insert, fresh session insert and prior credential revocation share one immediate transaction. Concurrent same-name registrations leave one account; insert/update failure rolls back all writes and leaves the prior valid session usable. Login rechecks the password hash/salt after asynchronous work before committing a fresh session, so a concurrent credential change cannot authenticate a stale password. Raw random 32-byte base64url account credentials are stored only as SHA-256 hashes. `watchnext_account_session` is separate from `watchnext_session`, HttpOnly/SameSite=Lax/Path=/, Secure on HTTPS, without cookie Expires/Max-Age; server absolute expiry is seven days in UTC Unix seconds. Duplicate cookie names are rejected. Rotation revokes only the presented previous account credential after success; logout revokes the current one and clears only the account cookie. Other browser sessions and legacy cookies remain independent. Every account-page read checks live expiry/revocation.

Registration independently generates a 32-byte random recovery code, persists only its SHA-256 digest and returns the raw code only in that immediate private response. The page offers copy/manual fallback and explicit saved-code Continue guidance. It keeps the code only in transient component memory, discards it on departure/restored navigation, and never writes local/session storage. Refresh, `/account`, and subsequent login have no retrieval operation. Passwords/recovery/session credentials are never application logs, query parameters or retained browser artifacts. Use the existing privacy launchers; don't export auth responses, DOM, cookies, screenshots, HAR or traces. Backup files contain digests and must still remain private.

## Private offline-code recovery — issue #33

`/login` links to dynamic `/recover`, which collects username, saved recovery code, new password and confirmation. It uses the same explicit body-only POST, bounded JSON reader, exact configured-origin/Fetch Metadata defense, focused feedback and pending duplicate prevention as #32. `POST /api/account/recover` allows only `username`, `recoveryCode`, `password`, `confirmation`; account/member IDs and return targets are rejected. Recovery ignores account cookies as proof/target authority, including duplicate or unrelated-account cookies. Only normalized username and the exact current canonical 32-byte base64url code can authorize a reset.

Recovery hashes the submitted canonical code and compares fixed-size 32-byte digests with `timingSafeEqual`; unknown/malformed stored accounts use an all-zero dummy expected digest. Invalid usernames and wrong/missing/malformed/consumed codes all receive the same generic 400 proof error. Invalid proof performs bounded digest work and **no expensive password derivation**. Valid proof applies #32 exact password/confirmation rules and shares the real default-cost native scrypt pool. No whole-request timing identity is claimed. Codes are offline saved material, valid until consumption/replacement without an arbitrary wall-clock expiry.

Separate process-local recovery maps admit five attempts per normalized username (all malformed usernames share one invalid bucket) and thirty total per fixed 15-minute window, reserving before proof. They use the existing bounded expiring storage and shared 2-active/8-waiting/30-second hash pool; successful reset clears its own name key. Failed proof, including unknown/malformed input, consumes admission but never changes credentials or locks ordinary login. Parse/origin/size failures are rejected before crypto access. Process restart resets these attempt limits; no distributed or permanent account-lockout protection is claimed.

After valid proof, derive a random-salted password outside SQL, generate a fresh random 32-byte code, then `BEGIN IMMEDIATE`: conditional account update by stable ID **and still-current old recovery digest**, replace all password/version/parameters and code digest, and revoke every live session of that target account. Zero updated rows means a consumed/racing code and rolls back. Forced failures roll back all writes, retaining old code/password/sessions. No recovery session is issued. A concurrent old-password login rechecks its captured hash/salt before insertion; a login committed before reset is revoked with the other sessions. Unrelated accounts, memberships, legacy cookies and every title/contribution/history/provenance value are untouched.

Only committed success returns the replacement code in a private/no-store/no-referrer response. It clears the current browser's account cookie even when that cookie was for another account, without revoking that unrelated server session. The once-only replacement view explains old-code invalidation/all-session sign-out and offers copy/manual fallback plus Continue to fixed `/login`; normal fresh login is required. Secret inputs clear on failure, username stays. Departure/reload/back restoration cannot fetch the raw code from application persistence. A network-lost success may already have consumed the old code; the UI tells the user to try the new password and explains that an undisplayed replacement cannot be retrieved. Lost password plus code has no email/support/profile bypass.

The bounded choices implement the existing delegated defaults. [OWASP recovery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html), inspected October 18, supports single-use secure proof, normal login after reset and session invalidation; its offline-method distinction supports the saved-code lifetime. No external channel, certification, new dependency or schema change is introduced.

## Account groups and live ownership — issue #34

`/account` offers real Create account group, Open group and explicit pending Join controls. Names use the existing 1–80-character validation. Creation atomically inserts a fresh account-mode group, immutable owner, fresh member, membership and hashed invitation, then selects it in this browser session. First membership uses the account username and a deterministic existing-palette color. Repeat joins and permitted rejoins retain the same member ID and personal history. An owner has no contributor editing privilege until contributing. There is no profile claiming, conversion, name matching or history copying from legacy groups.

Protected JSON `POST /api/groups/create`, `/switch`, `/join` and `/legacy` share the configured-origin, Fetch Metadata, bounded-body and private-response controls above. All require the current account session and its exact `revision`; create additionally permits only `groupName`, switch only `groupId`, and join/legacy no other fields. IDs supplied by the caller never establish membership. Create returns the private raw invite once, with copy/manual fallback. Open group selects only a live active membership; each account browser session has independent selection.

Account `/invite/<token>` validates the actual current-generation, nonrevoked invite and stores only a hash of a new random private continuation credential, for ten minutes, capped at 1000 pending rows after expired cleanup. The HttpOnly continuation cookie resumes through fixed `/login` or `/account`, without a token-bearing return query or private group name before authentication. GET never joins. Explicit protected Join rechecks session revision, pending intent, invite generation/revocation and membership in one transaction; it consumes the intent only with successful membership/selection. Removed members can rejoin only through a newer generation than their removal, preserving their original member ID. Expired/stale intents provide safe retry guidance. Creator removal/rotation controls are described below under #35.

`watchnext_access_mode` is a public enum in an HttpOnly session cookie, not an authentication credential. Account mode requires a valid separate account session, selected account group and live active membership on every request; it never falls back to a legacy cookie. Legacy mode requires a live legacy session. Only the backward-compatible legacy-cookie-only case works without an explicit mode; mixed credentials without a mode fail closed. Explicit mode/group selection advances monotonically persisted context revisions, including away-and-back switches. Account pages and hard navigation after authentication discard old page state; the existing legacy selector is shown only in legacy mode.

All product reads derive the selected group server-side, and own writes derive its actual account member. Captured Server Action context binds mode/session/group/member/revision, independently of caller form IDs, and is revalidated before transactions. Account mutations without matching context fail. Async metadata work rechecks the same context after awaiting; provider refresh additionally requires a current active contributor on a nonarchived title before fetch and before applying. Reviews and picker cycles bind the actual context, never an empty or legacy-cookie fallback. Account viewers contain active memberships only; removed-member attribution/history remain readable. Legacy picker/profile-selection context excludes the currently selected own profile, so selecting one's profile does not change chosen viewers; own history writes still bind that profile. Rejected requests cannot fetch/repair foreign targets. Existing global deadline-only imported-field expiry remains independent housekeeping, as clarified in the issue; it can physically remove already-due acquired fields without granting access or changing user-origin/history data.

## Creator participant and invitation controls — issue #35

Account `/group` renders actual active/inactive memberships with existing names/colors/status. Only the immutable creator sees Remove participant and Rotate invite; creator self-removal is absent and rejected on the server. Ownership grants no contributor metadata privilege. Legacy mode keeps its existing profile UI and has no management controls. Missing/expired/duplicate credentials, wrong mode/group, noncreator, stale context and unsafe origins fail before writes.

Protected JSON `POST /api/groups/remove` accepts only `contextKey`, `memberId`, `membershipGeneration`; `/rotate` accepts only `contextKey`, `expectedGeneration`. The context is an equality check against fresh session/membership authority, never authority by itself. The existing bounded body/configured-origin/Fetch Metadata and private/no-store/no-referrer behavior applies. Inside an immediate transaction, removal rechecks creator and target group/lifecycle generation. It records current invitation generation and removal time once. Repeated same-epoch removal returns `already_removed` without extending the cutoff; a stale confirmation after rejoin rejects. Every subsequent member request is denied across all sessions; in-flight provider work is discarded and #34's membership-generation binding prevents old actions/reviews/cycles reviving after rejoin. Account sessions for unrelated groups remain valid.

Removal never deletes a member, contribution or title, never autoarchives a sole-contributor title, and never changes personal progress/ratings/notes or acquired/user metadata. Current members see retained historical attribution marked Inactive participant; new picker viewer lists omit inactive memberships. These are readonly labels, including archive reuse; legacy attribution is unchanged. Existing mandatory deadline-only provider expiry remains independent housekeeping.

Rotation requires explicit confirmation, atomically compares displayed current generation, increments exactly once, revokes prior unrevoked invitation rows and inserts a fresh random 32-byte invitation hash. Generation overflow or any storage failure rolls back the entire operation. Replayed/competing old generation rejects with reload guidance rather than rotating again. Active members keep access. Removing at generation g bars every link/intent issued at or before g, even a link rotated before removal or discovered afterward. Only a newly obtained valid post-removal generation g+1 can restore the same membership/member/history; old pending intents never upgrade themselves.

Only explicit committed owner success returns the raw new `/invite/<token>` URL. Copy/manual fallback and localhost-only clarity are provided. Departure, reload and back restoration clear the transient field/state; no database/API retrieval exists. Losing the response/link requires another deliberate confirmed rotation. Inputs, routine logs/traces, return URLs, persisted browser storage and retained reports never receive the raw credential. Confirmation headings and announced pending/error/success feedback receive focus; Cancel is local and writes nothing. Error states retain the intended confirmation, with Reload group to resolve uncertain/stale state before retry.

## Create a group — issue #7

The Group entry page `/` submits `groupName` through `app/actions/create-group.ts`. The server operation uses `db/server.ts` and the existing initialized SQLite database. It does not read request Host/forwarded headers to construct links and does not establish a session, create a member, or select a profile.

### Input and validation

- `groupName` must be text. Trim outer JavaScript Unicode whitespace; accept 1–80 Unicode code points after trimming. Preserve internal whitespace and display case. Reject blank/whitespace-only, overlong, non-text/File, and embedded-NUL values on the server before database access.
- Same display names are allowed: each successful submission creates a distinct group ID and invitation. Names are not authentication or unique group identity.
- The form associates field errors with the input, retains what was entered, announces pending/error feedback, and disables fields/submission while an action is in flight. A later deliberate submission remains available, labeled Create another group after success.

### Origin configuration

**`WATCHNEXT_APP_ORIGIN`** is server-only configuration, loaded by Next from the environment or untracked `.env.local`. Default when unset: **`http://127.0.0.1:3000`**. See [the database guide](database.md) for the separate `WATCHNEXT_DATABASE_PATH` setting and explicit database initialization.

An explicit value must be an HTTP/HTTPS origin, with an optional single trailing slash, and no credentials, non-root path, query, or fragment. Empty/blank values, whitespace-surrounded values, URI shorthand, and normalized-away paths are rejected, not replaced with the default. Canonical URL origin serialization removes the allowed trailing slash/default port and normalizes hostname case. Never infer this setting from Host or forwarded request headers.

Example: `https://watch.example/` yields an invite on that configured origin; this is parser behavior, not a hosted service. The delivered launchers bind 127.0.0.1; use the [local setup](local-setup.md) origin/port consistently. The parser recognizes local aliases/127/8/::1 for the same-computer warning, but that does not make the launcher listen on every such address. Public/LAN hosting is outside this release, not a #30 deployment task.

### Transaction and invitation credential

`lib/groups.ts` validates input/configuration, calls `node:crypto.randomBytes(32)`, and base64url-encodes those 32 bytes (256 bits of entropy; 43 URL-safe characters). It uses independent random UUIDs for the group/invitation IDs. Inside one `BEGIN IMMEDIATE` transaction it inserts exactly one group and one invitation, committing together or rolling back both on an error. No member or session record is created.

Only `SHA-256(token)` as lowercase hex is persisted in `invitations.token_hash`. The raw token is present only in memory and the returned/displayed URL; it is not written to database fields, logs, fixtures, or repository files. Keep returned URLs private, avoid logging action responses, and redact them from any screenshots or retained debugging artifacts. A hash cannot reconstruct a link, so this operation does not promise to redisplay a lost raw token later.

Delegated first-release policy: invitation credentials do **not** expire automatically. `revoked_at` is initially NULL. Invitation resolution in [#8](https://github.com/xiaodlb/watchnext/issues/8) validates token shape, hashes it identically, rejects revoked/unknown invitations, and establishes group access under the trust-based model. Revocation/rotation UI, email invites, and accounts remain outside this increment.

The URL format is `<configured origin>/invite/<token>`. Issue #8 implements resolution and a token-free `/group` destination; issue #9 adds profile creation and selection there. A loopback URL still works only on the same computer.

### Returned state and UI behavior

The action returns one safe discriminated state:

| `kind` | Fields | Meaning |
| --- | --- | --- |
| `idle` | none | Initial client state |
| `invalid` | `nameError` | Field-associated validation failure; no write |
| `error` | `message` | Retryable origin/storage failure; no success URL, SQL, local path, stack trace, or raw credential |
| `created` | `name`, `inviteUrl`, `loopback` | Trimmed saved name and the private one-time returned URL |

Database exceptions are caught without logging them. A synthetic invitation-insert failure is tested to roll back the newly inserted group. The UI retains the controlled group name through failure, shows no stale success URL for that failure, and permits retry. A disabled in-flight form prevents accidental second submission; it is not a general idempotency/account/rate-limit system.

The invite URL is read-only, keyboard-focusable, and selected on focus. Copy invite link calls Clipboard API `writeText` with exactly the displayed URL, announcing success only after the promise resolves. Missing Clipboard API or rejected permission displays instructions to select/copy manually; the field remains available and retry stays enabled. No automatic email/message is sent.

## Invitation resolution and browser sessions — issue #8

`GET /invite/<token>` accepts only the canonical 43-character base64url representation of exactly 32 bytes. Decode/re-encode equality rejects alternate encodings of the same bytes. SHA-256 lookup must find a non-revoked invitation. Missing `/invite`, malformed, unknown, revoked, or storage-unavailable requests redirect to the same generic `/access-error` page without revealing group data or replacing an existing valid cookie. The error page has a real Return to Group entry link.

A valid invitation creates a fresh 32-byte random opaque session credential, stores only its SHA-256 hash in `group_sessions`, and sends it as a cookie before a 303 redirect to **`/group`**. The redirect stays on the request origin so the host-only cookie remains usable even when a local alias was used. Invitation responses set `Cache-Control: no-store` and `Referrer-Policy: no-referrer` so the bearer path is not forwarded as a referrer to the destination. Do not build links using request headers; new invite links still use the configured origin.

Cookie policy: `watchnext_session`, **HttpOnly**, **SameSite=Lax**, **Path=/**, no Domain, Max-Age, or Expires. Secure is enabled for an HTTPS request or configured HTTPS origin. It is a browser-session cookie: reload retains context, a separate browser context has no access, and browser session restoration can retain cookies. Closing a browser is not a guaranteed server revocation event.

The server session row binds the hash to one group and backing invitation, with optional `active_member_id`. Every access checks the current session, existing group, and non-revoked backing invitation. Deleted/unknown sessions and revoked/missing invitations cannot retain access. Server rows have no automatic expiry in this first-release policy; explicit row deletion or backing-invitation revocation invalidates them. This does not create an invitation expiry scheme. Later operational cleanup may remove unused rows without changing group/history records.

Opening a valid different-group invitation atomically inserts the new session and removes the browser's prior session row, sets the new cookie and clears active-member context. Invalid invitations leave the old context untouched. Reopening the same group rotates the credential while retaining any real same-group selected member; it never fabricates one or changes personal history. No profile UI is supplied by #8. The additive `0002_group_sessions.sql` migration includes group-consistent invitation/member foreign keys; existing migrations remain immutable. Run `pnpm db:init` after pulling it.

`/group` is dynamically rendered and calls the server guard before rendering any private group name. Missing/stale/forged access renders the generic error content. Valid access shows the real name and the profile selector, explaining that anyone with the invite can select a name/profile **without verifying personal identity**.

### Reusable read and mutation guard

App code imports `getActiveGroup` / `requireRecordAccess` from server-only `lib/access.ts`. The latter delegates to `lib/request-access.ts` and checks both session validity and the target's actual group in the database. Supported target kinds are group, title, and member; the kind selects fixed server-owned SQL. It never treats a submitted group ID as authority. If a payload contains a group ID, it must match the validated session and the actual target ownership. Unknown and wrong-group records produce the same safe `AccessError`.

Future reads call this guard before returning data; mutations call it with `mutation: true` before writing. Mutations additionally require POST/PUT/PATCH/DELETE, an exact Origin match to validated `WATCHNEXT_APP_ORIGIN`, and no cross-site Fetch Metadata. Missing Origin is denied. Next Server Actions also retain their framework same-origin protection; no wildcard allowed-origins configuration is added. SameSite and cookie possession alone are not the mutation protection. [Next Server Action protection](https://nextjs.org/docs/app/guides/data-security#allowed-origins-advanced)

Focused test-only request handlers exercise actual guard calls before reading/updating synthetic records. They demonstrate same-group success, known other-group denial, forged payload group rejection, missing/malformed/fabricated/stale cookies, revoked invitations, missing/cross-origin mutation headers, and unchanged denied records. No debug API or unrelated CRUD endpoint is shipped. Caller endpoints must catch `AccessError` and return generic access errors; do not serialize internal session/group data or raw database errors accidentally.

### Credential logging boundary
